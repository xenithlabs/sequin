⏺ The bug is real — I confirmed it in the merged code and fixed it.

  The bug

  lib/sequin/sinks/meilisearch/client.ex:90 (pre-fix) advanced the budget with
  elapsed_ms + delay — only the Process.sleep backoff. The Req.get between
  sleeps was free. Each poll inherits receive_timeout: sink.timeout_seconds from
  base_request (client.ex:303), so with a slow or hung Meilisearch, a handful
  of polls could burn 20–30s of wall clock while elapsed_ms still read a few
  hundred ms. The loop then kept going past the 25s guard, overran the
  consumer's 30s ack_wait_ms, and produced exactly the nack → redeliver →
  no-backfill-progress loop the commit set out to prevent.

  The fix

  - Monotonic deadline computed once in wait_for_task/2 and threaded through the
  recursion, replacing the accumulated elapsed_ms. Every iteration checks real
  remaining time.
  - Sleep clamped to remaining budget, so the last backoff can't overshoot.
  - Per-poll receive_timeout capped at the remaining budget (min of that and the
  sink's configured timeout). Without this, the deadline check still can't fire
  until a hung request returns — a single stalled poll could blow the budget
  even with correct accounting. This is beyond what CodeRabbit flagged, but the
  deadline isn't actually enforceable without it.

  I also added a regression test that stubs 500ms-per-poll responses and asserts
  the total stays inside the 1.5s test budget; the old accounting would have
  taken ~4s.
